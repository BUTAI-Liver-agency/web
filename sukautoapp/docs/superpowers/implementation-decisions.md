# 実装中に下した判断の記録

TikTokスカウトCRM PoC（株式会社BUTAI向け）の実装で、設計書に書かれていなかった、
あるいは設計書・実装計画の誤りを正すために下した判断の一覧。

各項目は「何を決めたか — なぜ — 間違っていた場合に何が起きるか」の形で記録している。
星山が内容を確認し、必要なら覆すための材料。

---

- Ruling: git worktree ではなく feature ブランチで隔離する — 新規プロジェクトでリポジトリ自体が存在せず、隔離すべき既存作業がない。worktree にするとコードと docs/ が別ディレクトリに割れて扱いにくい — 間違っていた場合のコスト: ほぼゼロ（ブランチは後からいくらでも組み替えられる）
- Ruling: T1 Step 1〜3 を書き換え、`npm create vite` を廃して手動スキャフォールドにした — 非空ディレクトリでの scaffold は対話プロンプトで停止するか docs/ を削除する。設計書・実装計画の消失は復旧困難で、リスクが対価に全く見合わない。あわせて scaffold 前提で内容が欠けていた package.json / tsconfig.json / vite.config.ts / index.html / src/main.tsx / src/App.tsx の内容を計画に明記した — 間違っていた場合のコスト: 手動構成が Vite の既定とずれる可能性があるが、ビルドとテストが通るかで即座に検知できる
- Ruling: T1 Step 10 から `git init` を削除した — セットアップ時点で初期化済みのため — 間違っていた場合のコスト: なし（`git init` は冪等）
- Ruling: React 19.3 のインストールを受け入れる（計画の Tech Stack には「React 18」と書いていた） — `npm install react` が現行メジャーを解決した結果であり、本計画はレガシーAPIを一切使わないため React 19 で完全に動く。ダウングレードは利益がなくリスクだけ増える — 間違っていた場合のコスト: ほぼゼロ（package.json でのピン留めで後から戻せる）
- Ruling: EBADENGINE 警告（node 20.18.1 vs 一部推移依存が要求する 20.19.0）を許容する — 実際に入った vite は 6.4.3 で engines が `^18 || ^20 || >=22`、node 20.18.1 を満たす。vite build と vitest の両方が通ることをコントローラ側で実行確認した — 間違っていた場合のコスト: 後続タスクでビルドが落ちれば即座に判明する。その場合は Node のアップグレードを利用者に依頼する
- Ruling: CSVヘッダ判定を前方一致から完全一致（かつ大文字小文字非依存）へ修正する — `lines[0].startsWith('handle')` は、ヘッダの無い入力でハンドルが "handle" で始まる実データ行をヘッダと誤認し、rows にも unparsedLines にも入れずに無言で捨てる。設計書6.1は「除外した件数と理由を担当者に見せる」ことを要求しており、痕跡を残さない取りこぼしはその趣旨に反する。修正は1行で、リスクは無い。レビュアーが Minor として挙げた大文字ヘッダの誤認（bogus候補者の混入）も同じ1行で同時に解消されるため、まとめて直す — 間違っていた場合のコスト: ほぼゼロ（ヘッダ文字列が将来変わった場合に定数を更新する必要が生じる程度）
- Ruling: テスト欠落2件を修正する — 実装は正しいが「既存側ハンドルの正規化」を固定するテストが1本も無く、`byHandle.set(candidate.tiktokHandle, ...)` への単純化リファクタが全テストを通過したまま重複スカウトを復活させうる。重複防止は設計書10の必須テスト項目であり、テストで固定されていない安全機構は安全機構ではない。オプトアウトと対象外が重なった場合の優先順位も同様に未固定 — 間違っていた場合のコスト: テスト3本分の追加工数のみ
- Ruling: レビュアーが Minor とした「toInsert のハンドル正規化が未固定」も同じ修正に含める — Task 11 の insertCandidates が row.tiktokHandle をそのままDBの一意制約列へ書くため、ここが正規化されないと大小文字違いの重複がDBをすり抜ける。Minor ではなく重複防止の一部と判断した — 間違っていた場合のコスト: ほぼゼロ（テスト1本）
- Ruling: レビュアーが design note として挙げた「markUnder18 が ageVerifiedBy/ageVerifiedAt を null にして監査証跡を消す」懸念は、変更不要と裁定する — 計画の Task 15 は markUnder18 の遷移のうち age_status と stage のみを永続化し、検証者フィールドには一切書き込まない（計画 3249-3252 行で確認）。DB 上の「誰がいつ確認したか」は保持される。純粋関数の戻り値に null が乗ることと、それが永続化されることは別 — 間違っていた場合のコスト: Task 15 実装時にこの2フィールドまで書き込む実装になっていれば証跡が消える。Task 15 のレビュー時に明示的に確認する
- Ruling: sentMessages の絞り込みが呼び出し側責務であることを JSDoc に明記する — ApprovalTarget は候補者IDを持たず関数側で自衛できないため、「テンプレBは1候補者につき1回まで」という保証はこの暗黙の前提だけに乗っている。文書化が無いと、将来の呼び出しが全件を渡した時点で制限が静かに壊れる。なお現在の Task 15 呼び出し側は messages.filter(m => m.candidateId === current.id) で正しく絞っていることを確認済み — 間違っていた場合のコスト: JSDoc 2箇所のみ
- Ruling: Task 6（送信ペース制御）と Task 7（文面ガード）を1回のディスパッチにまとめる — どちらも「ドメインモジュール1本＋テスト1本、計画に全文のコードあり、相互依存なし」という同じ形で、スキルの「小さく同形の作業はバッチにする」指針に合致する。レビューは1本にまとめるが、contentGuard の正規表現（日本語句点の誤検出回避）には個別に追跡指示を出す — 間違っていた場合のコスト: どちらかが修正ループに入った場合、もう一方も同じループを待つことになる（小さいモジュールなので影響は限定的）
- Ruling: レビュアーの「上限が回避できる」という主張は**誤り**と判定した — コントローラ側でトレースした結果、呼び出し側（new Date().toISOString()）も sentAt もUTCで揃っており、どの24時間窓でも上限は破れない。ただし指摘の本質（集計の「1日」がJST 09:00区切りになっている／`+09:00` 形式が混ざると日付バケットが壊れる）は正しい — 間違っていた場合のコスト: なし（この判定は修正方針を変えない）
- Ruling: countSentOn を日本時間基準に正規化し、slice(0,10) をやめて Date.parse による解釈に変える。toJstDate / todayInJst を追加し、Task 15 の当日判定もそれを使うよう計画を更新した — PoCの目的は実運用の数字を測ることであり、担当者の「今日」と集計の「今日」がJST 09:00でズレたまま計測するのは筋が悪い。また Postgres の timestamptz は `+09:00` 形式で返ることがあり、Z表記と混在すると同じ瞬間が別の日に入って上限集計が壊れる。Date.parse ならどちらの表記も正しく解釈される — 間違っていた場合のコスト: 日付境界の扱いが変わるため、PoC初日の集計が想定とズレる可能性。テストで両表記と境界を固定して検知可能にした
- Ruling: buildMessage の置換を単一走査方式に修正する — replaceAll を連鎖させると `{intro}` を置換した結果に対して `{ref_code}` の置換が走るため、AI生成文に `{ref_code}` という文字列が含まれていると、そこにも合言葉が差し込まれる。候補者のコメントがそのままAIプロンプトに入る設計なので、これは候補者が書いた文字列を起点とする混入経路。とりわけテンプレBは「合言葉を持たない」ことが前提であり、混入すると設計書4.1の計測前提が崩れる。テンプレート原文を1回だけ走査すれば、置換した内容が再走査されることはない — 間違っていた場合のコスト: ほぼゼロ（挙動は通常入力では同一で、回帰テスト2本で固定する）
- Ruling: 空の生成結果を失敗として扱い再試行する — trim 後に空文字になると checkContent が違反ゼロを返すため `{ ok: true, intro: '' }` となり、実モデル接続後に空行から始まるDMが候補者に届く。IntroViolation 型を本モジュール内に定義し、contentGuard（承認済み）には手を入れない — 間違っていた場合のコスト: ほぼゼロ（型の拡張のみ、tsc で全呼び出し側を検証済み）
- Ruling: レビュアーが Minor とした候補者コメントの区切りなし埋め込みも同時に修正する — 候補者のコメントがそのまま指示プロンプトに入る構造で、出力側の禁止語チェックは「月収」等は捕まえるが「1〜2文だけ」という形式を壊す誘導は捕まえない。外部の人間が書いた文字列が指示として解釈されうる経路を、プロンプト3行で塞げるのに残す理由がない — 間違っていた場合のコスト: プロンプトが少し長くなる程度
- Ruling: 候補者の削除経由で送信記録が失われる経路を塞ぐ — messages には UPDATE/DELETE ポリシーを置かず改変不能にしたはずが、messages.candidate_id が on delete cascade かつ candidates の RLS が for all（DELETE を含む）だったため、担当者が候補者を1件消すだけで送信記録が全て物理削除された。設計書8は送信記録を「トラブル発生時に事務所を守る唯一の証跡」と定義しており、これを消せる経路は残せない。修正は (a) FK を on delete restrict に (b) videos と candidates の for all を select/insert/update に分割し、どのテーブルにも DELETE ポリシーを与えない。これは設計書5.2が既にオプトアウトについて採っている「UIからは解除できない／必要ならDB側で対応」と同じ方針であり、新しい判断ではなく一貫性の回復 — 間違っていた場合のコスト: 候補者や動画の削除が必要になった場合にDB側での操作が必要になる。PoCでは計測が目的なので行の削除自体が想定されない
- Ruling: 合言葉コードの衝突回避を採番時に行う — 4桁32文字種は約105万通りで、候補者1000人規模だと誕生日問題により約38%（2000人で85%）の確率で衝突する。ref_code は一意制約つきで insertCandidates はバッチ挿入のため、1件の衝突で取り込み全体が Postgres エラーで失敗し、担当者には原因が分からない。事務所の目標は月500〜1000人なので1〜2ヶ月で踏む。判断はドメイン層（generateUniqueRefCode）に置き、データ層は既存コードの列挙のみ担当 — 間違っていた場合のコスト: 取り込みのたびに既存コードを1クエリ読む。PoC規模では無視できる
- Ruling: addCollectedCount を不可分な加算に変える — 読み取ってからJavaScript側で加算して書き戻す方式のため、2人が同時に取り込むと片方の件数が上書きで失われ、しかもエラーが出ない。この数値は設計書11が「最重要」と定めた指標（募集動画1本あたりのコメント数）であり、PoCが測ろうとしている当のものが静かに欠けるのは看過できない。Postgres 側の関数で加算する（security invoker で RLS を維持） — 間違っていた場合のコスト: マイグレーションに関数が1つ増える
- Ruling: updateCandidate の patch の age_status / stage をドメインの列挙型にする — bare string だと stage: 'sent' のような誤値が型チェックを素通りし、Postgres まで到達して初めて失敗する。ドメイン型は同ファイルで既に import 済みで、コストゼロで型の網が戻る — 間違っていた場合のコスト: なし
- Ruling: レビュアーが Minor とした findByRefCode の全角未対応も修正する — 候補者はスマホの日本語IMEで合言葉を打つため ＢＴ－４Ｘ７Ｋ の形で届きうる。担当者がそのまま貼ると「該当なし」となり LINE到達が記録されず、設計書11の主要指標が静かに過少計上される。severity より「主要指標に直結するか」で判断した — 間違っていた場合のコスト: 正規化が過剰に働く可能性だが、テストで全角・半角・長音記号を固定した
- Ruling: 合言葉の競合について「解決した」というレポートの記述を実態に合わせさせた — 同時実行する2つの insertCandidates は互いの未コミットのコードを見られないため競合窓は残る。ただし失敗は一意制約違反として明示的に起き、データ破損はない。窓が狭まっただけであり閉じてはいない。リトライ機構は追加しない（同時取り込み時に約0.25%という確率に対して複雑さが見合わない） — 間違っていた場合のコスト: 極めて稀に取り込みが失敗し、担当者が再実行する必要がある
- Ruling: 生成エンドポイントに認証を入れる — デプロイすると /api/generate は誰でも到達でき、1リクエストごとに有料モデルを呼ぶ。URLが漏れれば事務所の費用で無制限に課金される。Vercel の Deployment Protection でも塞げるが、利用者が設定し忘れたら守られないものを境界とは呼べない。アプリには既に Supabase 認証があるので、セッショントークンをサーバー側で検証する — 間違っていた場合のコスト: セッションが切れた状態で生成すると 401 になる。UIに明示的なエラーが出るため検知できる
- Ruling: 入力長の上限を入れる。ただしハンドラに直書きせず、ドメイン層の parseIntroRequest として実装する — 本プロジェクトは「判断はドメイン層、外側は受け渡しに徹する」構造で通してきた。上限値もルールであり、テストで固定できる場所に置く。上限は表示名100文字・コメント500文字（TikTokのコメント上限は150文字程度） — 間違っていた場合のコスト: 長いコメントが弾かれる可能性。境界値（ちょうど500は通る／501は弾く）をテストで固定した
- Ruling: レビュアーが Minor とした「想定外の応答形と本当に空の応答が区別できない」も修正する — サーバー側ログにブロック種別だけ記録する。実運用で原因が追えなくなるのを避けるため。利用者には出さず、モデルの出力内容や候補者データも記録しない — 間違っていた場合のコスト: なし
- Ruling: catch-all ルートの欠落を Task 14 に折り込んで修正する — 未マッチのパスでナビゲーションバーだけの白い画面になり担当者が行き止まりになる。ただし修正は1行であり、専用の実装＋レビュー往復は割に合わない。Task 14 はもともと App.tsx を編集するため、そこで同時に入れる — 間違っていた場合のコスト: Task 14 のレビュー範囲がわずかに広がる
- Ruling: 5件すべて修正する。いずれも同一コンポーネント内で、まとめて直せば「担当者が結果を信用できる画面」になる — 間違っていた場合のコスト: コンポーネントが1.5倍程度に長くなる
- Ruling: jsdom のダウングレードを受け入れる — Task 1 で監視事項としていた Node 20.18.1 の問題が顕在化したもの。jsdom は開発依存でしかなく本番挙動に影響しない。Node を 20.19 以上に上げれば override を外せる旨を最終報告に記載する — 間違っていた場合のコスト: テスト用DOMが1世代古いままになる。レビュアーが「テストが空振りしていないか」を検証し、disabled 判定が実DOM属性を読んでいることを確認済み
- Ruling: エラー処理・クリップボード失敗・生成中の承認・二重送信・読み込み失敗の区別、計5点を修正する — 最悪ケースは insertMessage 成功後に updateCandidate が失敗し、送信記録は残るのに候補者がキューに残って二度目のDMが飛ぶこと。設計書が防ごうとしている当の失敗であり、しかも担当者には何も表示されない — 間違っていた場合のコスト: コンポーネントが長くなる
- **Ruling: レビュアーの「送信記録を書くのは担当者が実際に送った後にすべき（TikTokを開いてから確認ボタンを押させる）」という提案は採用しない** — 失敗の向きが非対称。「記録は残ったが送っていない」は事務所のログが過大になるだけで候補者に害はない。「送ったのに記録が無い」は同じ人への二度目のDMを生み、本プロジェクトが防ごうとしている当の害。先に記録する方が安全側に倒れる。ただし指標（LINE到達率の分母）が過大計上されうるのは事実なので、コード内コメントと運用手順に明記する — 間違っていた場合のコスト: 担当者が承認後に送信をやめた場合、その分だけ送信数が過大に出る。運用手順に記載して人間が認識できるようにした
- Ruling: Task 16（合言葉ルックアップ）と Task 17（パイプライン）を1回のディスパッチにまとめる — どちらも「データ層を呼んで表示し、ステージを更新する」だけの小さな画面で、相互依存がない。スキルの「小さく同形の作業はバッチにする」指針に合致する — 間違っていた場合のコスト: どちらかが修正ループに入ればもう一方も待つ
- Ruling: レビュアーの指摘2（終端ステージから能動的パイプラインへ戻せる）は、**実物を読むと到達不可能**だった — かんばんが ACTIVE_STAGES の列しか描画しないため、対象外・連絡不要の候補者はそもそも画面に出ない。ただし逆向きは実害があり、ドロップダウンで「連絡不要」を選ぶとフラグが立たないまま候補者が画面から消え、UIから確認も修復もできなくなる。指摘の本質は正しいので、到達可能な形に合わせて直す — 間違っていた場合のコスト: なし（どちらの向きも塞ぐ修正にした）
- Ruling: ステージ遷移の判断をドメイン層の canChangeStage として切り出し、テスト12本で固定する — 「対象外（17歳以下）・辞退・連絡不要から戻せない」「進んだ候補者を巻き戻せない」は本プロジェクトが守っている保証そのもので、コンポーネントの if に埋めるとテストで縛れない。TERMINAL_STAGES は既に ageGuard と importFilter が参照しているのに、パイプラインだけが見ていなかった — 間違っていた場合のコスト: 正当な巻き戻しが必要になった場合はDB側での操作が必要になる。設計書5.2の「UIからは戻せない」方針と一貫している
- Ruling: かんばんに全11ステージの列を出す — 元は進行中6列のみで、誤って「辞退」にした候補者が画面から消えて確認もできなかった。表示したうえで戻せないことを明示する方が誠実 — 間違っていた場合のコスト: 列が横に広がる（overflowX は既に設定済み）
- Ruling: ドロップダウンから「対象外」「連絡不要」を外す — どちらも対応するフラグ（age_status / opted_out）とセットで初めて意味を持つ。ステージだけ変わると取り込み時の除外が効かず、同じ人が再びキューに現れる — 間違っていた場合のコスト: なし（専用の操作から設定できる）
