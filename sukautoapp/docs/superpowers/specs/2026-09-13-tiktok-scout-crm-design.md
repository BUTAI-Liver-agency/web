# TikTokスカウトCRM 設計書

- 作成日: 2026-09-13
- ステータス: 設計確定（実装計画は未作成）
- 対象: ライバー事務所向け スカウト業務支援ツール（クライアント納品物）
- 段階: PoC（軽量先行検証）

---

## 1. 背景と目的

ライバー事務所が、TikTokの募集投稿に反応した人へ個別にアプローチし、ライバーを獲得する業務を支援する。

当初の要望は「投稿にいいね・コメント・保存した人へ自動でDMを送る」だったが、後述の制約により実現不可能な部分がある。そこで本設計では、実現可能な範囲に要件を組み替えたうえで、より本質的な価値を中心に据える。

**本ツールの本質は「DM送信の自動化」ではなく「スカウト活動のパイプライン管理と計測」である。**

事務所が本当に必要としているのはDMが飛ぶことではなく、ライバーを獲得できることであり、そのためには「どの動画・どの文面・どの担当者が成果に結びついているか」が見えなければならない。DM作成の省力化は、その上に乗る副次的な価値として位置づける。

## 2. 前提と制約

### 2.1 技術的に実現できないこと

TikTokは自分の投稿に対して、**いいねしたユーザーの一覧も、保存したユーザーの一覧も公開していない**。APIにも存在せず、アプリのUIからも辿れない。分析画面で得られるのは件数のみ。

したがって「いいね・保存した人へDMを送る」は、自動化以前に**送信対象を特定できない**ため実現不可能。

**特定可能な反応者:**

| 反応 | 特定可否 |
|---|---|
| コメント | 可（公開情報） |
| フォロー | 可 |
| シェア／デュエット／スティッチ | 可 |
| DMを送ってきた人 | 可 |
| いいね | **不可** |
| 保存 | **不可** |

### 2.2 要件の組み替え：コメント誘導

募集投稿の本文で「興味がある人はコメントしてください」と誘導し、**コメントした人を見込み候補者とする**。

いいね・保存は「なんとなく気になる」レベルの反応だが、コメントは明確な意思表示であり、スカウト用途では母数より質が重要である。本組み替えは要件の劣化ではなく、対象精度の向上と位置づける。

**この制約（いいね・保存したユーザーは特定不可）は事務所へ説明済みであり、合意が取れている。** 本設計の出発点となる前提のため、合意事項として記録する。

### 2.3 DM送信の制約

- TikTokには一般公開された**DM送信APIが存在しない**。こちらから一斉にDMを送る正規ルートはない
- 完全自動化はブラウザ自動操作に依存し、**TikTok利用規約違反およびアカウントBANのリスク**を負う
- 本設計では**半自動方式**を採用する。文面生成・宛先管理・履歴管理はツールが行い、**送信ボタンを押すのは人間**とする

### 2.4 受信側の制約

- 16歳未満のアカウントはDM機能自体が無効（要確認事項に記載）
- 「友達のみ受信」設定のユーザーにも届かない

**そのため、送信不可の相手が構造的に一定数存在する。** ツールは「送信不可」をステージとして扱い、公開コメント返信によるプロフィール誘導へフォールバックできるようにする。

### 2.5 運用前提

| 項目 | 内容 |
|---|---|
| 送信元 | 事務所公式アカウント1つ。担当者アサインはツール側で管理 |
| 担当者数 | 4〜10名 |
| 目標送信数 | 月500〜1000件 |
| 対象年齢 | **18歳以上のみ。17歳以下にはスカウトを行わない**（事務所方針） |
| 顧客のAIポリシー | 確認済み・外部AI APIの利用および候補者データのクラウド保存は問題なし |

### 2.6 目標送信数とペース制限の矛盾

目標は月500〜1000件だが、公式アカウント1つからの安全な送信ペースを保守的に**1日20件**と置くと、稼働20日で**月400件**となり目標に届かない。

**対処方針（PoCで判断する）:**

1. PoCで安全ラインを実測し、上限を引き上げられるか確認する
2. 届かない場合は、以下のいずれかで埋める
   - (a) 送信元アカウントを増設する（ただし公式アカウントの信頼性という利点は薄まる）
   - (b) 一部を公開コメント返信によるプロフィール誘導へ振り替える

PoC段階では**1日20件から開始し、UIから上限を変更可能**にしておく。

## 3. スコープ

### 3.1 作るもの

| # | 機能 | 目的 |
|---|---|---|
| 1 | 候補者の取り込み（コピペ／CSV） | 母数計測の起点 |
| 2 | 候補者パイプライン（6ステージ） | 製品の中核 |
| 3 | AI文面生成＋テンプレート管理 | 作業時間の削減 |
| 4 | 送信キュー（承認→クリップボードコピー→TikTok起動） | 日次の作業画面 |
| 5 | 担当者アサイン | 4〜10名運用に必須 |
| 6 | 安全機構（年齢・重複・オプトアウト・ペース・URL・ログ） | 事務所の信用保護 |
| 7 | 歩留まり計測（動画別／テンプレ別／担当者別） | 事業判断の材料 |

### 3.2 作らないもの（PoCでは）

- **TikTok API連携** — 並行して開発者申請のみ提出し、審査結果を待つ
- **自動送信** — 半自動の原則を維持。コード上に自動送信経路を実装しない
- **返信の自動取り込み** — 返信有無は担当者が手動更新する
- **本格的な認証・マルチテナント・課金** — 1事務所向けの簡易ログインで足りる

## 4. 中核コンセプト：候補者パイプライン

### 4.1 ネクストアクションの設計

事務所が候補者に求める最終行動は「公式LINEから代表へMTGを依頼してもらうこと」である。導線は以下の通り。

```
TikTok DM → HPを読む → 公式LINEを登録 → 合言葉を送る → MTG
```

**この導線には計測が切れる箇所がある。** 候補者がLINEへ移った時点で、TikTok側の候補者データと結びつかなくなり、「どの動画から来た人が契約したか」が追えない。またHPを読んでそのままLINEへ進む候補者はTikTok上で返信しないため、**返信率は成果指標として機能しない**。

**対策：合言葉コード方式**

候補者1人ごとに一意の短いコード（例 `BT-4X7K`）を発行し、DM文面に含める。

> 「公式LINEで、最初に『BT-4X7K』とだけお送りください」

LINEでコードを受け取った側がツールにコードを入力すると、候補者が特定されステージが進む。URLパラメータによる引き継ぎはLINE側の仕様制約を受けるため、**合言葉方式のほうが確実かつ実装が軽い**。

### 4.2 ステージ定義

```
① 見込み（コメント検知）
   ↓
② DM送信済み
   ↓
③ 反応あり  ← TikTokでの返信、またはLINE到達のいずれか
   ↓
④ LINE到達（合言葉で特定）  ← 実質的なコンバージョン地点
   ↓
⑤ MTG設定
   ↓
⑥ 契約
```

**③と④は独立して発生しうる。** TikTokで返信せず直接LINEへ来る候補者が一定数いるため、③を経ずに④へ進む経路を許容する。

上記に加え、以下の終端ステージを持つ。

- **送信不可** — DM設定により届かない相手
- **対象外** — **17歳以下と判断した相手**、または募集条件（女性ライバー）に合致しないと担当者が判断した相手。恒久除外
- **無反応** — 一定期間、返信もLINE到達もない
- **辞退** — 本人が断った
- **オプトアウト** — 今後の連絡を拒否（永久除外）

### 4.3 計測できるようになること

- どの募集動画から契約ライバーが生まれたか
- どのDMテンプレートの**LINE到達率**が高いか
- 担当者ごとのLINE到達率・MTG化率の差

**主要指標はDM返信率ではなくLINE到達率とする。** 返信率は補助指標に留める。

## 5. データモデル

```
Video（募集動画）
  - url, title, posted_at
  - comment_count_collected   ← 取り込んだコメント数（母数計測用）

Candidate（候補者）
  - tiktok_handle             ← 一意制約。重複防止のキー
  - ref_code                  ← 一意。LINEで名乗る合言葉（例 BT-4X7K）
  - display_name
  - comment_text              ← 取得元のコメント本文
  - source_video_id           → Video
  - age_status                ← unverified / under18 / adult（既定は unverified）
                                unverified と under18 は送信不可
  - stage                     ← パイプラインのステージ
  - assignee_id               → User
  - opted_out                 ← 真の場合、恒久的に除外
  - created_at, updated_at

Message（送信記録）
  - candidate_id              → Candidate
  - template_id               → Template
  - body                      ← 実際に送信した全文
  - sent_at, sent_by          → User

Template（文面テンプレート）
  - name, body
  - allowed_age_status        ← このテンプレを使える年齢状態

User（担当者）
  - name, email, role
```

### 5.1 重複防止

`Candidate.tiktok_handle` に**一意制約**を設ける。同一人物が複数の募集動画にコメントしても、候補者は1件に集約され、送信キューに二度現れない。

同じ人物へスカウトDMを重複送信することは、事務所の信用を直接損なう事故であるため、アプリケーションロジックではなく**データベース制約で担保する**。

### 5.2 オプトアウトの扱い

TikTokのDM内で「今後の連絡は不要」と伝えられた場合、**担当者が手動で `opted_out` を立てる**。自動検知は行わない（誤検知で連絡すべき相手を失うリスクのほうが大きいため）。

一度立てたフラグはUIから解除できない。解除が必要な場合はデータベース側での対応とする。

### 5.3 再アプローチ回数の制限

テンプレB（再アプローチ）の使用回数は、`Message` テーブル上で当該候補者かつ `template_id = B` の件数を数えて判定する。1件以上存在する場合、テンプレBは選択不可とする。専用のカウンタ列は持たない。

### 5.4 年齢の扱い（17歳以下は対象外）

事務所の方針により、**スカウト対象は18歳以上に限定する。17歳以下へはDMを送らない。**

**ただしTikTokは他ユーザーの年齢を公開しないため、システムによる自動判定は不可能である。** この制約下で方針を担保するため、以下の三重の仕組みを置く。

| # | 仕組み | 内容 |
|---|---|---|
| 1 | **既定で送信不可** | `age_status` の既定値は `unverified`。この状態では承認ボタンが押せない |
| 2 | **担当者の明示的な確認** | 担当者がプロフィール・投稿内容を確認し、「18歳以上であることを確認した」を明示的に選択して初めて送信可能になる。**誰がいつ確認したかを記録する** |
| 3 | **文面での明示** | 全テンプレートの固定部分に「18歳以上の方を対象としています」を含める |

17歳以下と判断した候補者は `under18` を設定し、**ステージを「対象外」へ移す。以後キューに再出現しない**（オプトアウトと同等の恒久除外）。

#### 設計上の限界（明記しておく）

**仕組み2は担当者の目視判断であり、年齢の真正性を保証するものではない。** TikTok上で年齢を確証する手段は存在しないため、これはツールで解決できる問題ではない。

本設計が担保するのは以下の2点に限られる。

- 確認を経ずに送信することが**構造的に不可能**であること
- 誰がいつ確認したかの**証跡が残る**こと

**実際の年齢の確定は、LINEでのやり取りおよび代表面談の段階で事務所が行う運用とする。** その運用ルールの策定は事務所側の責任範囲であり、要確認事項に記載する。

## 6. 画面設計

送信作業はTikTokアプリへの受け渡しを伴うため、**送信キューはスマートフォン（PWA）**、管理系はPCでの利用を想定する。

### 6.1 取り込み画面

コメントを貼り付け、またはCSVをアップロードすると、パースして候補者化する。

取り込み時に以下を自動で除外する。

- 既に登録済みの `tiktok_handle`
- `opted_out` が真の候補者

差分のみが新規追加され、除外件数と理由が表示される。

### 6.2 送信キュー画面（メイン）

カード1枚が候補者1人に対応する。

**カードの表示内容:**
- 相手のアイコン・ハンドル・表示名
- コメント全文
- 取得元の募集動画
- **年齢状態バッジ**（未確認・17歳以下は赤で常時表示。この状態では承認不可）
- **「18歳以上であることを確認した」チェック**（未チェックでは承認ボタンが無効）
- AI生成を含む送信文面（その場で編集可能）
- 本日の残り送信枠

**操作:** 承認すると文面をクリップボードへコピーし、TikTokのDM画面を起動する。スキップすると次のカードへ進む。

**設計目標は「1人あたり数秒」**。この速度を満たせない設計は、日次25〜50件の運用に耐えない。

### 6.3 パイプライン画面

ステージ別のかんばん表示。担当者は自分の担当分のみに絞り込める。ステージの変更はドラッグまたは選択で行う。

### 6.4 ダッシュボード画面

以下の歩留まりを表示する。

- 動画別（コメント数 → 送信数 → 返信数 → 面談数 → 契約数）
- テンプレート別（送信数 → 返信率）
- 担当者別（送信数 → 返信率 → 面談化率）

## 7. AI文面生成

### 7.1 事務所情報（文面の固定部分に使う事実）

出典: https://butai-liver-agency.github.io/web/index.html

| 項目 | 内容 |
|---|---|
| 会社名 | 株式会社BUTAI |
| 代表者 | 横山 舞 |
| 事業 | ライバーマネジメント、ライブ配信支援、クリエイターブランディング |
| 募集対象 | 女性ライバー／**18歳以上** |
| 訴求点 | 所属費用無料／未経験・副業可／学業・仕事との両立支援／ライバー経験者が伴走 |
| 報酬の扱い | TikTokアプリ規定に準拠。**収入額は保証しない**とHPに明記 |
| ネクストアクション | HPを読み、公式LINEから代表へMTG依頼 |

**HPが「収入を保証しない」と明記している点は、本設計の禁止事項（7.3）と完全に一致する。** 文面がHPより踏み込んだ約束をすることは、事務所自身の表明と矛盾するため許容しない。

### 7.2 原則：AIに全文を書かせない

AIの守備範囲を**冒頭の1〜2文のパーソナライズ部分に限定する**。

```
[AI生成]   相手のコメント内容に触れた1〜2文
[固定文面] 事務所紹介 / 訴求点 / 対象年齢の明示 / HPへの案内 / 合言葉つきLINE導線
```

**限定する理由:**

1. **事実誤りの防止** — 報酬・契約条件・サポート内容をAIが生成すると、事務所が表明していない内容を伝えることになる。スカウト文脈では致命的なトラブルに直結する
2. **承認速度の確保** — 目視対象が1〜2文なら数秒で判断できる。全文生成では毎回精読が必要となり、設計目標を満たせない
3. **効果測定の成立** — 固定部分がテンプレートとして揃っているからこそ「テンプレAのLINE到達率が高い」と言える。全文が毎回異なると比較が成立しない

### 7.3 生成の制約

プロンプトで以下を明示的に禁止する。

- 報酬額・収入・収益の言及
- 成果や収入の保証、およびそれを示唆する表現
- 契約条件・期間・ノルマへの言及
- 断定的な勧誘表現
- **URLの記載**（スパム判定回避のため。導線はプロフィール欄のリンクに統一する）

さらに**実行時に禁止ワードおよびURLパターンのチェック**を通す。検出時は生成をやり直し、再検出時は担当者へ警告を表示する。

**文面の最終的な責任は承認する担当者にある。** この前提は承認画面上にも明示する。

### 7.4 テンプレートA（初回）ドラフト

```
{AI生成：相手のコメントに触れた1〜2文}

はじめまして。ライバー事務所の株式会社BUTAIです。

所属費用は無料で、未経験の方や、学業・お仕事と両立しながら
活動される方をサポートしています。ライバー経験のあるスタッフが
配信の準備から一緒に進めます。

※18歳以上の方を対象としたご案内です。

もしご興味があれば、まず弊社のHPをご覧ください。
プロフィール欄のリンクから開けます。

読んでみて「少し話を聞いてみたい」と思われたら、
HP内の公式LINEから、合言葉「{ref_code}」とだけお送りください。
代表の横山が直接ご相談に乗ります。

※LINEのご連絡は所属のお約束ではありません。
　話を聞いたうえで、続けるかどうかはご自身で決めていただけます。
```

末尾の一文は、HPの「友だち追加は所属契約ではない」という表明と揃えている。**スカウト詐欺への警戒が強い領域であり、ハードルを下げる効果と、事務所の姿勢の一貫性の両方を担う。**

### 7.5 テンプレートB（再アプローチ）ドラフト

短く、押しつけない。**1候補者につき1回まで**をシステムで制限する。

```
{AI生成：前回のコメントに触れた1文}

以前ご連絡した株式会社BUTAIです。
もしまだご興味があれば、プロフィール欄のリンクからHPをご覧ください。
（18歳以上の方を対象としたご案内です）

不要でしたら、このままで大丈夫です。失礼しました。
```

### 7.6 テンプレート一覧

| ID | 用途 | 使用条件 | 回数制限 |
|---|---|---|---|
| A | 初回 | `age_status = adult` のみ | 制限なし |
| B | 再アプローチ | `age_status = adult` かつ テンプレA送信済み | 1候補者につき1回 |

**17歳以下・年齢未確認に使えるテンプレートは存在しない。** 事務所方針により、そもそも送信対象外であるため。

## 8. 安全機構

| 機構 | 実装内容 |
|---|---|
| **年齢ガード** | `age_status` が `adult` 以外の候補者は**承認ボタンが無効**。担当者が「18歳以上であることを確認した」を明示選択して初めて解放され、確認者と日時を記録する。`under18` は「対象外」ステージへ移し恒久除外 |
| **送信ペース制御** | 1日の送信上限を設定値で管理（初期値20件）。キューに残り枠を表示し、上限到達で以降は翌日扱い。送信時刻も分散させる |
| **オプトアウト** | 連絡拒否の意思表示を受けた相手を `tiktok_handle` で恒久除外。取り込み時に自動で弾く |
| **重複防止** | `tiktok_handle` の一意制約＋送信履歴チェック |
| **URLガード** | 生成文面にURLが含まれていないことを送信前に検査。スパム判定の回避 |
| **全件ログ** | 誰がいつ誰に何を送ったかを `Message` に全保存。年齢確認の記録も含む。トラブル発生時に事務所を守る唯一の証跡 |

### 8.1 自動送信経路を実装しない

「送信」操作の実体は**クリップボードへのコピーとTikTokアプリの起動のみ**とする。TikTokへ直接送信するコードを一切持たないことで、将来の改修で誤って自動送信が混入する余地を構造的に断つ。

## 9. 技術構成

4〜10名が同一の候補者データを共有するため、ローカル完結は成立しない。

| 層 | 選定 | 理由 |
|---|---|---|
| フロントエンド | React（Vite）＋ PWA | 送信キューをスマホで、管理画面をPCで使い分けられる |
| データベース／認証 | Supabase（Postgres + Auth） | 一意制約を含むリレーショナルな要件に適合し、認証込みで立ち上げが速い |
| AI | Claude API（`claude-sonnet-5`） | 文面生成 |
| ホスティング | Vercel | PoC規模では十分かつ低コスト |

## 10. テスト方針

TDDで進める。**壊れると事務所の信用が失われる3点**に自動テストを集中させる。

1. **重複防止** — 同一 `tiktok_handle` が二度キューに乗らないこと
2. **オプトアウト** — 除外済み候補者が取り込みで復活しないこと
3. **年齢ガード** — `age_status` が `adult` 以外の候補者を承認・送信できないこと、および `under18` が「対象外」から復活しないこと

加えて以下をテストする。

- 送信ペース上限を超えて承認できないこと
- テンプレBが同一候補者に2回適用できないこと
- AI生成結果に禁止ワードおよびURLが含まれないこと（実行時ガードと二重で担保）

UIの見た目はPoC段階では手動確認とする。

## 11. PoCの検証計画

PoCの目的は、ツールの完成ではなく**事業判断に必要な数字を得ること**である。

| # | 計測項目 | 判断内容 |
|---|---|---|
| 1 | **募集動画1本あたりのコメント数** | **最重要。** 目標送信数に対して母数が足りるか。不足なら本企画そのものが成立しない |
| 2 | 取り込み→送信完了までの所要時間 | 省力化効果の実測 |
| 3 | **LINE到達率**（送信数 → 合言葉受信数） | **主要指標。** 導線全体が機能しているか |
| 4 | DM返信率 | 補助指標。文面の初速 |
| 5 | LINE到達 → MTG化率 | 代表面談への接続の質 |
| 6 | テンプレート別・動画別・担当者別の差 | 改善余地の所在 |

検証期間は1〜2ヶ月を想定する。

## 12. 要確認事項（未解決・事務所または一次情報での確認が必要）

本設計は以下の事実認識を前提としている。いずれも公式情報での裏取りが必要である。

| # | 項目 | 影響 |
|---|---|---|
| 1 | TikTokの年齢別DM制限（16歳未満はDM不可という認識） | 送信不可率の見積もり。なお本設計は18歳以上のみを対象とするため、この制限は送信可否の判定には用いない |
| 2 | いいね・保存したユーザー一覧が本当に取得不可か | 本設計の出発点。覆る場合は要件から再検討 |
| 3 | TikTok Business APIでのコメント取得可否と日本での申請可否 | 方式1（API連携型）への移行可否 |
| 4 | 1アカウントあたりの安全な1日送信数 | 公開情報がないため保守的に開始し実測で調整 |
| 5 | **18歳以上であることの確認方法（運用ルール）** | ツールは「確認したという記録」までしか担保できない。LINE・面談段階での確認手順は事務所側で定める必要がある |
| 6 | **TikTok DM本文にURLを記載した場合のスパム判定・リンク挙動** | 実機検証が必要。本設計はURLを記載しない前提だが、前提の妥当性確認として |
| 7 | **合言葉コードの運用体制** | LINEでコードを受け取り、ツールに入力するのは誰か（代表か担当者か）。運用が回らないとLINE到達率が計測できない |
| 8 | TikTokプロフィールのリンク欄にHPを設置済みか | 本設計の導線の前提 |

## 13. PoC後の展開

PoCと並行してTikTok開発者申請を提出し、結果に応じて分岐する。

- **審査通過** → 方式1（公式API連携型）。コメント取り込みを自動化する
- **審査不通過** → 方式2（スクリーンショットOCR取り込み）。TikTokの審査・規約に依存せず動作する

いずれの分岐でも、パイプライン・テンプレート・安全機構・計測基盤はそのまま流用できる。**PoCで作るものが無駄にならない構成**を意図している。
